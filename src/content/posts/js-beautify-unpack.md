小程序、插件、H5 壳解包之后，JS 经常只剩一两行：空白没了，变量名被压扁，字符串和正则挤在一起。这通常不是解包失败，而是构建链做过压缩 / 混淆：

- 删除空白、换行和注释
- 变量名、函数名压缩
- 合并表达式和控制流
- 字符串转义或拆分
- 打包成单文件 / 再过混淆器

**解包**和**可读化**是两件事。前者拿文件，后者让人能读。后续还可以继续做变量重命名、字符串整理和逻辑分析。

## 别对整文件瞎正则

直接 `re.sub` 改关键字，在 JS 里很容易误伤：

```js
const text = "const value = 1";
const re = /const\s+value/;
// const value should remain in this comment
```

如果直接搜 `const`，字符串、正则字面量和注释里的内容也可能被改掉。替换一次后后面字符位置会变，继续用旧偏移就会改错。

更稳的三段式：

```text
扫描受保护区域
    → 只在普通代码区做正则 / 偏移编辑
    → 交给 JS 美化器重新排版
```

## 保护区域 + 倒序应用编辑

### 先识别受保护区域

至少要保护：

- `'...'` / `"..."` / `` `...` ``
- `//` 与 `/* */`
- 正则字面量 `/.../flags`（和除法区分开）

保护区域只记起止：

```python
ProtectedSpan(start=120, end=168)
```

之后规则只在这些区域之外跑。通用 JavaScript 变换应使用支持该语法的 parser / AST。下面的词法扫描仅适合已限定输入、识别失败就跳过的局部规则——否则 `/` 很难区分是除法还是正则开头。常见启发：看前一个有效字符是否在 `([{,:;=!&|?+-*%^~<>`，或前一个词是否是 `return` / `typeof` / `case` 等。

### 用编辑记录代替立即替换

不要在 `re.sub()` 回调里不断改原串，先记编辑：

```python
OffsetEdit(start=300, end=315, replacement="decodedValue")
```

一轮扫完后，按 `start` **从大到小**应用：

```python
for edit in sorted(edits, key=lambda e: e.start, reverse=True):
    source = source[:edit.start] + edit.replacement + source[edit.end:]
```

这样前面的偏移不会被后面的长度变化带崩。重叠编辑应直接报错，不要猜该留哪一个。

### 每条规则完成后重新扫描

如果一条规则改了长度，下一条不能复用上一轮的保护区域：

```text
规则 1：扫描 → 生成编辑 → 倒序应用
规则 2：重新扫描 → 生成编辑 → 倒序应用
规则 3：重新扫描 → 生成编辑 → 倒序应用
```

规则可以放 JSON：

```json
[
  {
    "pattern": "旧函数名",
    "replacement": "新函数名",
    "flags": ["I"]
  }
]
```

只有扫描和规则实现符合上述条件，才可以将编辑限定在代码区；模板字符串里的 `${...}`、正则与除法歧义、嵌套语法都需要处理。字符串、注释、正则字面量被刻意跳过。注意用的是 Python `re` 语法，不是 JS 正则的全部特性。

## 排版交给美化器

定点规则适合改个别符号；括号、对象、链式调用应交给 `jsbeautifier` 这类语法感知工具。常用策略：

- 默认四个空格缩进
- 保留有限原始空行
- 文件末尾补换行
- 美化前后都做 Node 语法检查

原稿引用的 `beatifual_js.py` 和工具目录的 `requirements.txt` 未随本仓库提供，因此也没有可核对的 `--dry-run`、备份或原子替换实现。这里不再将这些私有脚本参数作为可执行教程。纯格式化可使用 [Prettier 官方 CLI](https://prettier.io/docs/cli)，固定工具版本，并先在工作副本上运行：

```bash
node --check file.js
# 使用项目内已锁定版本的 prettier，而不是临时拉取未知版本
./node_modules/.bin/prettier file.js --check
./node_modules/.bin/prettier file.js --write
node --check file.js
```

这是假定你的工具目录已经安装 Prettier 的用法，不表示本博客项目含有该依赖。WXS、平台扩展语法和不同模块模式需另核对工具支持；Node 的语法检查不等于行为等价验证。

## 完整工作流

### 1. 保留原始解包目录

不要在唯一副本上反复试：

```text
unpacked-original/    原始解包结果（只读）
unpacked-work/        美化和分析目录
rules.json            项目专用规则
```

### 2. 先做纯格式化

先不启用自定义规则，看美化器能否正常解析。语法完整的代码，这一步通常就能恢复缩进、换行和块结构。

### 3. 再添加定点规则

只有确认某段文本确实需要修复时才加规则。每条规则应有明确输入、输出和作用范围，避免过宽的 `.*`。

### 4. 检查语法和差异

```bash
node --check file.js
```

批量结果还要看：

- 文件数量是否与解包目录一致
- 是否出现大量空文件
- 字符串数量是否异常减少
- `require` / `import` / 导出对象是否还在
- 关键函数调用前后是否一致

## 常见问题

### 美化器报错

先保留报错文件，检查 parser 和语法版本是否匹配，不以关闭检查后强制写回作为默认处理。分析差异时还要对照字符串、正则、自动分号插入和模块语义。

### 美化后仍然难以阅读

这说明问题已经超出排版范围：

- 变量名压缩到失去语义
- 控制流平坦化
- 字符串运行时拼接 / 解密

美化器只能恢复布局，不能凭空恢复原始变量名。下一步应结合调用关系、字符串 xref 和控制流逐步重命名，而不是继续堆全局正则。

### 正则规则没有命中

检查目标是否其实在字符串 / 注释 / 正则字面量里——保护扫描会故意跳过。再确认 pattern 是否按 Python `re` 写对了。

## 小结

```text
词法保护 → 定点编辑 → 美化器 → 语法检查 → 备份写回
```

脚本实现可以很朴素：一段保守的词法扫描 + 规则 JSON + `jsbeautifier`。本仓库没有提供这个完整流水线实现；文章本身只需要把这条边界守住——**字符串里的文本不是代码**。
